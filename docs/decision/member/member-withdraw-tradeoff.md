# 회원 탈퇴 기능 구현 트레이드 오프


## 배경

회원 정보 수정 화면에서 회원이 직접 탈퇴를 요청할 수 있도록 기능을 구현하였다.

회원 탈퇴는 단순히 `member` 객체의 데이터를 삭제하는 기능이 아니라 다음과 같은 사항들을 함께 고려해야 한다.

- 탈퇴 화면의 로그인 차단
- 기존 주문/ 결제 내역 보존 유무
- 진행 중인 주문이 있는 회원의 탈퇴 제한 정책
- 탈퇴 시 장바구니 데이터 정리 정책
- 탈퇴 후 동일 아이디/ 이메일 재사용 허용할 것인지

도서 쇼핑몰에서는 회원이 탈퇴하더라도, 과거 주문, 결제, 배송 이력은 관리자가 확인할 수 있어야 한다고 생각했다.

따라서 회원 데이터를 물리적으로 삭제하기 보다는 탈퇴 상태를 기록하여 접근을 제한하는 방식이 필요했다.

---

## 선택한 구조

### member

```sql
member
- member_id
- login_id
- password
- name
- email
- phone
- zipcode
- address
- address_detail
- member_type
- created_at
- updated_at
- withdrawn_at
```

회원탈퇴 시 `member` row를 삭제하지 않고 `withdrawn_at`을 갱신한다.

```sql
UPDATE member
SET
    withdrawn_at = #{withdrawnAt},
    updated_at = #{updatedAt}
WHERE member_id = #{memberId}
AND withdrawn_at IS NULL
```

로그인, 회원정보 조회, 장바구니, 주문 생성 등 사용자 기능에서는 `withdrawn_at IS NULL`조건을 이용하여 탈퇴 회원을 제외한다.

---

## 트레이드 오프 1. 회원 데이터를 물리적으로 삭제할 것인지, Soft Delete로 처리할 것인지.

### 대안 1. Hard Delete

회원 탈퇴 시 `member` 데이터를 실제로 해당 컬럼을 삭제하는 것이다.

```sql
DELETE FROM member
WHERE member_id = #{memberId}
```


#### 장점
- 구현이 단순하다.
- 탈퇴한 회원 데이터가 DB에 남지않는다.
- 조회 쿼리에서 탈퇴 여부 조건을 넣지 않아도 된다.

#### 단점
- 기존 주문, 결제, 배송 데이터와의 연관 관계가 깨질 수 있다.
- 외래키 제약 조건 때문에 주문/장바구니/결제 데이터를 함께 처리해야 한다.
- 관리자 주문 관리에서 과거 주문자의 정보를 확인하기 어렵다.
- 주문 이력 보존이 중요한 쇼핑몰 도메인과는 맞지 않는다.

### 대안 2. Soft Delete

회원 데이터를 삭제하지 않고 탈퇴 일자를 기록하는 방식이다.

```sql
UPDATE member
SET withdrawn_at = NOW()
WHERE member_id = #{memberId};
```

#### 장점
- 기존 주문, 결제, 배송 이력을 유지할 수 있다.
- 관리자 화면에서 과거 주문 내역을 계속 확인 가능
- 탈퇴 회원의 로그인만 차단하고 거래 내역은 보존


#### 단점
- 회원 조리 쿼리마다 `withdrawn_at IS NULL`조건을 고려해야한다.
- 탈퇴 회원의 아이디/이메일 재사용 정책을 별도로 정해야한다.
- 개인정보 보관 기간에 대한 정책이 추가적으로 필요하다.


### 결정

회원탈퇴는 Soft Delete 방식으로 구현했다.
쇼핑몰 서비스에서는 주문과 결제 이력이 중요한 거래 기록이기 때문에 회원 row를 물리적으로 삭제하지 않고 `withdrawn_at`을 갱신하는 방식을 선택했다.

## 트레이드 오프 2. 진행 중인 주문이 있어도 회원탈퇴를 허용할 것인지.

### 문제 상황

회원이 결제 완료 후 배송이 끝나기 전에 탈퇴할 경우 다음과 같은 문제가 발생할 수 있다.
- 배송 상태 변경 관리가 애매해진다.
- 고객 문의나 배송 문제 발생 시 대응이 어려워진다.
- 주문은 존재하지만 회원은 탈퇴한 상태가 되어 서비스 정책이 복잡해진다.

### 대안 1. 진행 중인 주문이 있어도 탈퇴 허용

#### 장점
- 탈퇴 로직이 단순하다.

#### 단점
- 배송 중인 주문의 관리가 어려워진다.
- 탈퇴 이후 주문 상태 변경이나 고객에 대한 대응이 복잡해진다.


### 대안 2. 진행 중인 주문이 있으면 탈퇴 제한
```sql
SELECT EXISTS(
    SELECT 1
    FROM orders
    WHERE member_id = #{memberId}
    AND order_status IN ('PAID', 'PREPARING', 'SHIPPING')
)
```

#### 장점
- 배송이 완료되지 않은 주문의 정합성을 유지할 수 있다.
- 주문/배송 관리 흐름이 명확해진다.
- 회원탈퇴 전에 남은 주문을 먼저 처리하도록 유도할 수 있다.

#### 단점
- 사용자는 진행 중 주문이 끝날 때까지 탈퇴할 수 없다.
- 탈퇴 제한 상태에 대한 안내 메시지가 필요하다.

### 결정
진행 중인 주문이 있으면 회원탈퇴를 제한했다.
현재 프로젝트에서는 다음 상태를 진행 중 주문으로 판단했다.

## 트레이드 오프 3. 회원 탈퇴 시 장바구니 데이터를 유지할 것인지.

### 대안 1. 장바구니 데이터 유지

#### 장점
- 탈퇴 회원의 장바구니 기록까지 보존할 수 있다.
- 추후 복구 정책이 생기면 장바구니 데이터를 재사용할 수 있다.

#### 단점
- 장바구니는 주문/결제와 달리 보존 가치가 낮다.
- 탈퇴한 회원의 임시 데이터가 DB에 계속 존재하게 된다.

### 대안 2. 회원 탈퇴 시 장바구니 상품 삭제

```sql
DELETE ci
FROM cart_item ci
JOIN cart c
       ON ci.cart_id = c.cart_id
WHERE c.member_id = #{memberId}
```

#### 장점
- 탈퇴 회원의 임시 데이터를 정리할 수 있다.
- 장바구니 데이터가 불필요하게 쌓이는 것을 줄일 수 있다.


#### 단점
- 탈퇴 후 복구 정책이 정해지면 장바구니 복구는 어렵다.
- `cart` 자체를 남길지 함께 삭제할지 정책을 추가로 정해야한다.

### 결정

회원 탈퇴 시 `cart_item`데이터를 삭제했다.

장바구니는 주문 전 임시 보관 데이터이기 때문에 불필요하게 보존하면 메모리 낭비로 이어지게 될 가능성이 있다고 판단하였다.

## 최종 선택

회원탈퇴 기능은 다음 방식으로 구현했다.

```text
1. 로그인 회원 조회
2. 비밀번호 검증
3. 진행 중 주문 존재 여부 확인
4. 진행 중 주문이 있으면 탈퇴 제한
5. 장바구니 상품 삭제
6. member.withdrawn_at 갱신
7. 세션 무효화
8. 메인 화면으로 redirect
```
