# 도서 및 이미지 삭제 정책 결정

## 1. 배경

관리자 도서 삭제 기능을 구현하면서 다음 항목을 어떤 방식으로 처리할지 고민하였다.

```text
product 데이터
product_image 데이터
서버에 저장된 실제 이미지 파일
```

상품을 삭제할 때 모든 데이터를 즉시 제거할 수도 있고, 삭제 상태만 기록한 뒤 기존 데이터를 유지할 수도 있다.

---

## 2. 선택지 비교

### 1. Hard Deleted

상품과 이미지 데이터를 즉시 제거하는 방식이다.

```sql
DELETE FROM product_image
WHERE product_id = #{productId};

DELETE FROM product
WHERE product_id = #{productId};
```

실제 이미지 파일도 함계 제거한다.

#### 장점
- 사용하지 않는 데이터가 DB에 남지 않는다.
- 이미지 저장 공간을 즉시 회수할 수 있다.
- 조회 쿼리에 삭제 여부 조건이 필요없다.

#### 단점
- 실수로 삭제한 상품을 복구하기 어렵다.
- 상품 변경 이력을 확인할 수 없다.
- DB 트랜잭션이 롤백되어도 삭제한 실제 파일은 복구되지 않는다.

---

### 2. 상품만 소프트 삭제하고 이미지 유지

상품에 삭제 시간과 상태를 기록하는 방식이다.

```sql
UPDATE product
SET status = 'DELETED',
    updated_by = #{updatedBy},
    updated_at = NOW(),
    deleted_at = NOW()
WHERE product_id = #{productId}
    AND deleted_at IS NULL
```

`product_image` 데이터와 실제 이미지 파일은 유지한다.

#### 장점
- 실수로 삭제한 상품을 복구할 수 있다.
- 파일 삭제 실패로 인한 DB와 파일 시스템의 불일치를 피할 수 있다.
- 주문이나 운영 이력을 보존할 수 있다.

#### 단점
- 삭제된 상품 이미지가 저장 공간을 계속 사용한다.
- 모든 조회 쿼리에 삭제 여부 조건이 필요하다.
- 영구 삭제 기능이나 정리 정책이 별도로 필요하다.
---

### 3. 상품은 소프트 삭제하고 이미지는 즉시 삭제

상품 데이터는 유지하지만 이미지 DB 데이터와 실제 파일은 제거하는 방식이다.

#### 장점

- 상품 이력은 유지할 수 있다.
- 이미지 저장 공간을 즉시 회수할 수 있다.

#### 단점

- 상품을 복구해도 이미지를 복구할 수 없다.
- 소프트 삭제의 복구 가능성이 불완전해진다.
- DB 작업과 파일 시스템 작업의 원자성을 보장하기 어렵다.
---

## 최종 선택
현재 프로젝트에서는 다음 정책을 선택했다.

```text
product
→ 소프트 삭제

product_image
→ 유지

실제 이미지 파일
→ 유지
```

삭제된 상품은 조회 조건을 통해 화면에서 제외한다.

```sql
WHERE deleted_at IS NULL
```

상품 상태도 함께 변경한다.

```text
status = DELETED
deleted_at = 현재 시간
updated_by = 관리자 ID
```

---

## 5. 선택 이유

관리자 실수로 삭제된 상품을 복구할 가능성을 열어두고, DB와 파일 시스템 사이의 데이터 불일치를 방지하는 것을 우선했다.

상품 이미지를 즉시 삭제하지 않으면 저장 공간을 추가로 사용하지만, 현재 프로젝트 규모에서는 데이터 안정성이 저장 공간 절약보다 중요하다고 판단했다.

---

## 6. 향후 개선 방향

운영 환경에서는 이미지가 무기한 유지되지 않도록 별도의 영구 삭제 정책이 필요하다.

```text
상품 소프트 삭제
-> 일정 기간 보관
-> 스케쥴러가 삭제 대상 조회
-> 실제 이미지 파일 삭제
-> product_image 삭제
-> 상품 영구 상제 또는 보관
```

파일 삭제 실패에 대비해 다음 방법 또한 고려할 수 있다.

- 파일 삭제 실패 로그 기록
- 재시도 가능한 삭제 상태 관리
- 정기적인 미사용 이미지 정리 작업
- 클라우드 스토리지 LifeCycle 정책 적용
- 주문 이력이 있는 상품은 영구 삭제 제한

---

## 7. 결과

소프트 삭제를 적용하면서 다음 사항을 함께 고려하게 되었다.

- 삭제는 단순한 `DELETE` 쿼리가 아니라 비즈니스 정책이다
- 주문과 상품의 참조 관계를 고려해야한다.
- DB 트랜잭션은 실제 파일 삭제까지 롤백하지 못한다.
- 복구 가능성과 저장 공간 비용 사이의 균형이 필요하다.
