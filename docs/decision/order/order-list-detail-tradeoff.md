# 주문 내역 조회 및 상세 조회 트레이드 오프

## 배경

주문 생성 기능 이후, 사용자 주문 내역 목록 조회 및 주문 내역 상세 조회 기능을 추가하였다.

주문 조회 기능은 단순 목록 출력이지만, 다음과 같은 요구사항을 함께 고려해야 한다.

- 주문 당시 상품명과 가격 유지
- 로그인 회원 자신의 주문만 조회
- 마이페이지 요약 정보 제공
- JSP 화면 공통 영역 재사용


---

## 트레이드 오프 1. 주문 상세 조회 시 memberId + orderId로 검증

### 문제 상황

주문 상세 URL은 다음과 같다.
```text
GET /orders/{orderId}
```

`orderId`만으로 조회하면 다른 사용자의 주문번호를 추측해서 접근할 수 있다.

주문 상세에는 수령인 이름, 연락처, 주소, 결제 금액이 표시되므로 보안상 반드시 소유자 검증이 필요하다.

### 대안 1. orderId만으로 조회 후 서비스 로직에서 memberId 비교 후 검증

#### 장점
- 쿼리가 단순해진다.

#### 단점
- 다른 사용자의 주문 데이터가 애플리케이션 계층까지 올라온다.
- 검증 누락 시 개인정보 노출 위험이 있다.

### 대안 2. memberId + orderId를 함께 조건으로 조회

```sql
SELECT *
FROM orders
WHERE orderId = #{orderId}
AND memberId = #{memberId}
```

#### 장점
- DB 조회 시점에서 주문 소유자 검증이 이루어진다.
- 다른 사용자의 주문은 조회되지않는다.
- URL 조작에 의한 접근을 방어할 수 있다.

#### 단점
- 관리자 주문 상세 조회에 추가 쿼리가 필요하다.

### 결정

사용자 주문 상세 조회는 `memberId` + `orderId`를 함께 조건으로 조회했다.

조회 결과가 없으면 주문이 존재하지 않거나 로그인 사용자의 주문이 아니라고 판단해 예외 발생

## 트레이드 오프 2. 주문 목록 DTO와 주문 상세 DTO 분리

### 대안 1. 하나의 OrderResponse DTO를 사용해 조회

#### 장점
- DTO 클래스 수가 줄어든다.
- 초기 구현이 빠르다.

#### 단점
- 목록 화면에는 필요 없는 다른 정보들이 포함될 수 있다.
- 상세 화면에서 필요한 목록을 주문 목록 화면에서도 정보를 가지고 있게 된다.

### 대안 2. 각각의 목적에 맞게 DTO 분리

```text
OrderListResponse
- 주문 목록 조회에 필요한 대표 상품 정보

OrderDetailResponse
- 주문 상세의 배송 정보, 결제 정보 등

OrderDetailItemResponse
- 주문 상세의 각각의 상품에 대한 정보
```

#### 장점
- 화면별 필요한 데이터가 명확하다.
- 목록 조회와 상세 조회 쿼리가 각각 최적화하기 쉽다.
- 다른 기능 추가 시 코드의 변경 없이 DTO 추가로 확장성이 좋다.

#### 단점
- DTO클래스의 수가 늘어난다.

### 결정

주문 목록과 주문 상세는 화면에 표시할 정보들의 목적이 다르다.

따라서 각각의 별도 DTO 분리하는 방식을 선택했다.
