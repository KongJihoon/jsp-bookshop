# 주문 생성 기능 구현 트레이드 오프

## 배경

장바구니에 담긴 상품을 선택하여 주문서를 작성하고, 주문하기 버튼을 누르면 실제 주문이 생성되도록 구현하였다.

주문 기능은 단순히 주문 테이블에 데이터를 저장하는 것뿐 아니라 다음과 같은 흐름을 함께 처리해야한다.

- 주문 상품 검증
- 주문 당시 상품 정보 저장
- 재고 차감
- 주문 상품 저장
- 주문 완료 후 장바구니 상품 삭제
- 중간 실패 시 전체 롤백

따라서 주문 생성 로직은 하나의 트랜잭션으로 묶어 데이터의 정합성을 보장해야 한다.

---

## 테이블 설계

### 선택한 구조

```text
member 1 : N orders
orders 1 : N order_item
product 1 : N order_item
```

```sql
orders
- order_id
- member_id
- order_status
- receiver_name
- receiver_phone
- zipcode
- address
- address_detail
- total_price
- ordered_at
- canceled_at

order_item
- order_item_id
- order_id
- product_id
- product_name
- price
- quantity
- item_total_price
- created_at
```

### 선택 이유
주문은 장바구니와 달리 구매가 확정된 거래 기록이다.
따라서 현재 상품 정보를 계속 참조하기보다 주문 당시의 상품명, 가격, 수량을 저장해야한다.

상품명이 변경되거나 가격이 수정되더라도 과거 주문 내역은 주문 당시 기준으로 유지해야 한다.

---

## 트레이드 오프 1. 주문 상품에 상품명과 가격을 저장할 것인가

### 대안 1. product_id만 저장하고 상품 정보는 product에서 조회

#### 장점
- 데이터 중복 감소
- 정규화 관점에서 구조가 단순하다.
- 상품 정보 변경 시 항상 최신 상품 정보를 제시한다.

#### 단점
- 상품 정보나 가격이 변경되면 과거 주문 내역도 변경된 것처럼 보인다
- 주문 당시 거래 정보를 보존하기 어렵다
- 주문 이력의 불변성이 약해진다.

### 대안 2. 주문 당시 상품명과 가격을 order_item에 저장

#### 장점
- 주문 당시 상품 정보를 안정적으로 보존할 수 있다.
- 상품 정보가 변경되더라도 과거 주문 내역은 변하지 않는다.
- 주문 상세 조회 시 `product` 테이블에 대한 영향이 줄어든다.

#### 단점
- 상품명, 가격 정보가 중복 저장된다.
- 상품 정보 정합성을 `product`와 완전히 맞추는 구조가 아니다.

### 결정
`order_item`에 `product_id`와 함께 `product_name, price, quantity, item_total_price`를 함께 저장한다.


---

## 트레이드 오프 2. 주문 생성 시점에 주문서를 다시 검증할 것인가.

### 대안 1. 주문서 진입 시 검증한 데이터를 그대로 신뢰

#### 장점
- 구현이 단순하다.
- 주문 생성 시 추가 조회가 줄어든다.

#### 단점
- 주문서 페이지 진입 이후 상품 상태나 재고가 변경될 수 있다.
- 주문 생성 시점의 정합성을 보장하기 어렵다.

### 대안 2. 주문 생성 시점에 장바구니 상품을 다시 조회 후 검증

#### 장점
- 주문 생성 직전 상품 상태와 재고를 다시 확인할 수 있다.
- 다른 회원의 cartItemId 요청을 방어할 수 있다.
- 판매중지/ 삭제 상품 주문을 막을 수 있다.

#### 단점
- 주문 생성 시 추가 조회 로직이 필요하다.
- 서비스 로직의 복잡도가 증가.

### 결정
- 주문 생성 시점에도 `cartItemIds`를 기준으로 주문 상품을 다시 조회하고 검증했다.

---

## 트레이드 오프 3. 주문 생성 전체를 하나의 트랜잭션으로 처리할 것인가.

### 대안 1. 각 작업을 개별 처리
```text
orders 저장
재고 차감
order_item 저장
cart_item 삭제
```

#### 장점
- 각 작업이 독립적으로 실행한다.
- 구현 흐름을 단계적으로 보기 좋다.

#### 단점
- 중간 실패 시 일부 데이터만 저장될 수 있다.
- 주문 생성은 성공했지만 재고 차감이 안되는 문제가 발생 할 수 있다.

### 대안 2. 주문 생성 전체를 `@Transactional`로 처리

#### 장점
- 중간 예외 발생 시 전체 작업이 롤백된다.
- 주문, 재고, 장바구니 데이터의 정합성을 유지할 수 있다.
- 주문 생성의 원자성을 보장할 수 있다.

#### 단점
- 트랜잭션의 범위가 넓어질 수 있다.
- 외부 결제 API를 붙일 경우 트랜잭션 범위 재설계 필요.

### 결정
현재는 토스 결제 연동 전 단계이므로 주문 생성 전체를 하나의 트랜잭션으로 묶었다.
